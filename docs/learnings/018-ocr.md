# 018 — OCR capture (sheet → parse pipeline) (v1.2 PR 14)

Photograph or import a workout sheet → recognize each line → review → append the
confirmed lines to one session. The spec's framing is the whole design: **OCR is an
input source, not a new pipeline.** It produces text; the *existing*
deterministic→FM→confirm→write path does everything else. No second parser, no second
validator, nothing auto-saves.

## The seam: text in, the existing parser out

`TextRecognizing` is Foundation-only (returns `[RecognizedLine]` = text + confidence)
with the boundary at `Data` (encoded image bytes) so common code needs no
`UIImage`/`CGImage`/`Vision` type. The real `VisionTextRecognizer` lives entirely
inside `#if canImport(Vision)` (`VNRecognizeTextRequest`, `.accurate`, language
correction; observations sorted top-to-bottom by `boundingBox.minY`); `NoopTextRecognizer`
+ `TextRecognizerFactory` cover the no-Vision build. Same gating discipline as
FoundationModels (PR 8) and HealthKit (PR 10): zero SDK symbols in always-compiled
code, a fake drives the tests.

`OCRCaptureModel` then runs each recognized line through the **same**
`WorkoutParsing` the typed flow uses (defaulting to `WorkoutParserFactory.make`), and
`confirmAll()` writes via the **same** `WorkoutStore.save(_:into:)`. So OCR cost
nothing at the parse or storage layer — the spine thesis paying off again.

## One session, continued index, all-or-nothing

`confirmAll()` concatenates every included, parsed line's sets into **one**
`WorkoutDraft` and saves it `into: nil`, which reuses the active open session (or lazily
opens one). One transaction → one session → `set_index` continued from MAX+1 across all
lines. Reached from the Today tab, whose `reconcileActiveSession()` on appear already
retired any stale/cross-day session, so OCR appends to *today's* workout; the Today
sheet's `onDismiss` reconciles again so the banner reflects the new sets.

## Honest by construction — nothing auto-saves

- Each line is parsed but **not** written; `store.setCount()` is 0 until `confirmAll`
  (pinned by a test).
- A line the parser can't read (decline/clarification — OCR is non-interactive per
  line) becomes a **flagged, skip-by-default** candidate, never dropped silently and
  never guessed.
- A **bare scheme** ("3x10") parses to a *nameless* draft that couldn't be saved
  anyway, so it's treated as unreadable and flagged for editing rather than failing at
  confirm — a small honesty guard specific to OCR (the typed flow lets you name a bare
  scheme interactively; a scanned sheet line is expected to name its exercise).
- `confidence < 0.5` flags "review — OCR can misread" even on a line that parsed
  cleanly. Printed text usually clears it; handwriting often doesn't. The framing is
  assistive, the confirm list is the safety net.
- A failed confirm keeps the reviewed candidates (`backToReview`) so the user retries
  without re-scanning.

## Works without a camera

Import is `PhotosPicker` (out-of-process, needs no photo-library permission); the
camera (`OCRCamera`, a gated `UIImagePickerController` wrapper) is *optional* and only
offered when `isSourceTypeAvailable(.camera)`. Info.plist carries honest
`NSCameraUsageDescription` + `NSPhotoLibraryUsageDescription`. Denying the camera still
leaves full import + manual entry — the App Review 5.1.1 "works without the permission"
requirement (PR 15).

## SwiftUI detail worth recording

`candidates` is `@Published private(set)`, so the review list can't bind into it
directly. Each row is a dedicated `OCRCandidateRow` subview owning its edit text as
local `@State` (seeded from the candidate); edits commit back through an async closure
that calls `model.updateText` (which re-parses). Keeps the model the sole owner of
candidate state while still allowing inline editing.

## Not compiled here

No Vision/UIKit/Xcode on Linux. The recognizer protocol, the per-line parse routing,
the review/confirm/append logic, and the flag/skip/edit behavior are **unit-tested via
a fake recognizer + the real deterministic parser** (multi-line → N candidates; confirm
→ one session, set_index 1,2,3; unreadable flagged-not-saved; nothing before confirm;
edit re-parses; low-confidence flag; append to an existing open session). The gated
`VisionTextRecognizer`, `OCRCamera`, and the SwiftUI views are correct-by-inspection;
real recognition quality, the camera, and the permission prompts are a human-on-device
acceptance step. Vision symbol names follow the SDK docs — verify in Xcode.

## Review round

The bot caught a real 🔴: the review row committed edits only on `.onSubmit` (return),
so tapping **Save** after typing a correction without pressing return saved the *stale*
OCR parse — defeating the confirm-before-save safety net. The fix makes the save path
self-correcting rather than relying on the UI committing in time:

- The row syncs `text` to the model on **every keystroke** (`setText`, cheap, no
  parse), and commits a re-parse on **focus loss** as well as return (`@FocusState`).
- **`confirmAll()` re-parses every included line from its current `text` before
  saving** — the definitive guarantee that what's saved matches what's visible, even
  if no edit was ever submitted. A line edited into something unreadable is dropped
  rather than saved from its stale valid parse. Two tests pin both directions.

Two 🟡s also fixed: a `PhotosPicker` load/transfer failure now surfaces a visible
`.failed` state (`imageLoadFailed`) instead of a silent no-op; and an **explicit**
un-check is recorded (`userExcluded`) so a later edit/reparse can't silently
re-include a line the user chose to skip (the bot's question — it was unintentional).

A second round caught a narrower follow-on 🔴: two `commitEdit` Tasks for one row
(submit + focus-loss, or quick successive edits) can finish **out of order**, so an
older parse could overwrite a newer edit's *displayed* sets. (The *saved* data was
already safe — `confirmAll` re-parses from current text — but the visible state could
go stale.) Fixed with a per-row check: `commitEdit` applies its parsed result only if
the row's current `text` still equals the text it parsed; since `setText` keeps `text`
live on every keystroke, a superseded parse is simply dropped. Pinned by a test that
runs a stale commit after a newer edit and asserts the newer one stands. Also, on the
bot's `sourceText` question: the deterministic parser already stamps each set's
`sourceText` with the line it parsed (the *edited* text), so a corrected line carries
the correction, not the OCR misread; the `confirmAll` fallback now uses `candidate.text`
(not `originalText`) for consistency, and a test asserts the saved `sourceText` is the
corrected text.

Further rounds tightened the async edit/save lifecycle the bot kept probing: `setText`
is the single writer of `text` and `commitEdit` applies a parse only if the row's text
hasn't moved since (drops out-of-order/superseded parses — pinned by a true
`GatedParser`-actor race test); `confirmAll` re-parses **every non-excluded** row from
current text so an inline fix that was never committed still saves; `canConfirm`
requires a line that's already parsed *or* edited (so an untouched unreadable scan can't
enable a no-op Save) and a zero-parse confirm surfaces a `.failed` state instead of a
silent no-op; an edited line drops its OCR low-confidence flag (the confidence was the
recognizer's, not the user's text); and `confirmAll` is **single-flight** (`isSaving`
guard + disabled button) so a double-tap can't append duplicate sets. Finally, the
gated `VisionTextRecognizer` runs `VNImageRequestHandler.perform` on a
`Task.detached(.userInitiated)` (a `static nonisolated` helper) so recognition doesn't
block the `@MainActor` caller's main thread while the sheet shows `.recognizing`.

The save/checkbox contract took the most iteration. Final shape: a single
`willSave(candidate)` predicate drives the checkbox, toggle-enablement, the Save count,
and `confirmAll`'s snapshot, so the visible state can't diverge from what persists. The
subtle bug that took several rounds: an *edited* row is optimistically "will save" (the
edit gets reparsed at confirm), but once a commit has *already* reparsed it to no sets
it must drop out — else a committed-yet-unreadable row keeps a phantom check and
`confirmAll` silently omits it. Resolved with `lastParsedText` (the text `sets` was
parsed from): `hasPendingReparse` (`text != lastParsedText`) distinguishes "edit not
yet tried" (optimistically checked) from "known unreadable" (unchecked). And
`confirmAll` is **all-or-nothing**: if any checked line turns out unreadable at confirm
it saves nothing and reports how many to fix/skip rather than silently dropping it —
"what you saw checked is what saved."

## Review settled — remaining items are device-acceptance / optional

The review converged to clean (no red/yellow flags). Three follow-ups were left as
deliberate non-blockers:

- **On-device guarantee (reviewer's question): confirmed.** The Info.plist / picker copy
  ("the image and text never leave your phone") holds on the PR 8 base. Vision OCR and
  the deterministic parser are on-device; the FoundationModels layer is also on-device
  (Apple Intelligence runs locally) and only fires when the deterministic parse declines
  — and when it's unavailable, recognized text simply routes to the deterministic
  parser. No path transmits the image or recognized text.
- **Cancellation (optional):** `recognize` is *latest-request-wins* (discards a
  superseded result) but doesn't yet *cancel* the older Vision work. Not a correctness
  gap; could save CPU on very large images. Deferred — would need `Task` cancellation
  threaded into `VisionTextRecognizer`.
- **Reading order on real sheets (device acceptance):** `lines(from:)` originally sorted
  purely by `boundingBox.minY` (top-to-bottom). Multi-column or skewed sheets should still
  be sanity-checked on a device.

## Recovery + review round (PR #239)

PR #231 (the original OCR PR) merged into the **PR-8 feature branch**, but PR 8 had already
merged to `main` ~19h earlier — so OCR's "merged" badge was real yet its base was a stale
branch and **none of its files reached `main`**. Recovered by merging the intact OCR branch
onto current `main` in **PR #239** (one trivial `Info.plist` conflict — `main`'s HealthKit
strings + OCR's Camera/Photo strings → keep both).

Surmado review on #239 (no red flags) raised one actionable 🟡: **`lines(from:)` had a
Y-descending sort with no X tie-breaker**, so same-row / multi-column observations could
misorder, and `confirmAll()` persists in that order. Fixed by quantizing `minY` into row
bands (`rowBandHeight = 0.03`) and breaking ties left-to-right by `minX` — a strict weak
ordering over the derived `(band, minX)` key (no epsilon-compare transitivity trap). The
single-column common case is unchanged; the band logic was validated in Python. Multi-column
behavior on real sheets remains a device-acceptance check. Deferred (reviewer's other two,
both follow-ups): `Task`-cancellation of superseded Vision work, and a richer
previously-denied-camera fallback — both UX/perf judgment calls best made with device input.
